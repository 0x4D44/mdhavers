# Journal: Default-expr captures + masel defaults (2026-01-05)

## Goal
Fix LLVM backend correctness for default parameters that reference:
- outer variables captured by nested functions (especially when the nested function is returned as a value)
- `masel` when calling instance methods as first-class function values

Keep coverage guardrails intact (functions/instantiations = 100% under `scripts/coverage_guardrails.sh`).

## Repro / Symptoms
New LLVM integration tests failed:
- Returned closure + default referencing outer param:
  - error: `CompileError("Undefined variable: x")`
- Bound method value + default referencing `masel`:
  - error: `CompileError("'masel' used outside of a method")`

Repro:
- `timeout 900 cargo test --features llvm --test llvm_function_value_defaults`

## Root causes
1) **Capture discovery ignored parameter default expressions**
   - Nested-function capture analysis only scanned the function body.
   - If a default referenced an outer var (e.g., `a = x`), the nested function was treated as non-capturing, so calling it later outside the defining scope tried to compile the default without `x` in scope.

2) **`call_function_value` simple-function dispatch eagerly compiled method defaults**
   - The function-value dispatch generates IR for *all* candidate functions.
   - Method functions are present in `self.functions` and were included in the “simple Function tag” dispatch list.
   - When `f()` had 0 args, the dispatch’s default-filling attempted to compile defaults for method params without a bound `masel`, triggering the compile-time error even though the runtime call would be via the closure path.

3) **Closure construction boxed `masel`**
   - `compile_expr` closure construction was boxing *all* captures via `ensure_boxed_variable`.
   - But the calling convention treats captured `masel` as a direct value (not a boxed cell), so boxing it would make `masel.v` behave like a property access on a list cell.

## Changes
### 1) Capture discovery now scans defaults
- Updated `find_free_variables_in_body` to also collect free variables from `Param.default`.
- Added `params_use_masel` and extended nested-function predeclare logic in both:
  - `compile_function`
  - `compile_method_body`
  so `masel` is captured when it appears in defaults (not just in the body).

### 2) Method-aware default filling in `call_function_value` (simple Function tag)
- Precompute a `method_fn_names` set from `class_methods`.
- When dispatching a function pointer that corresponds to a method:
  - temporarily bind `current_masel` to the first argument (or `naething` if absent) while compiling default expressions
  - offset default indexing by 1 (defaults stored for user params only; LLVM signature includes leading `masel`)
  - never try to pull a “default” for the implicit `masel` slot

### 3) Don’t box captured `masel` when building closures
- In `compile_expr` (function-as-value closure construction), skip `ensure_boxed_variable` for `"masel"`.

### 4) Tests + coverage
- Expanded `tests/llvm_function_value_defaults.rs` with:
  - returned closure uses captured default
  - bound method value applies defaults using `masel`
  - returned closure from a method captures `masel` for defaults
- Added a unit test in `src/llvm/codegen.rs` to exercise `params_use_masel` in the `cfg(test)` crate instance, restoring instantiation coverage to 100%.

## Validation
- `timeout 900 cargo test --features llvm --test llvm_function_value_defaults` ✅
- `timeout 2400 bash scripts/coverage_guardrails.sh` ✅
  - functions: 100%
  - instantiations: 100%
  - hotspot ordering invariant OK (interpreter missed regions <= codegen)

## Notes / Follow-ups
- There’s still a broader semantic question: LLVM default evaluation currently happens at the call site, while the interpreter evaluates defaults in the callee’s closure environment. The new capture work addresses a major class of mismatches, but there may be shadowing edge-cases to explore later.
- Next exploratory targets:
  - nested defaults referencing earlier params (interpreter supports this; LLVM may need explicit bindings)
  - arity mismatch behavior for first-class function calls (current LLVM behavior pads/truncates to keep IR valid)
