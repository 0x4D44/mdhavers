# Journal: Core default-parameter semantics follow-ups (2026-01-05)

## Goal
Keep tightening “core language” semantics around default parameters, beyond the earlier closure-capture fixes:
- method defaults should work consistently across call forms (direct call vs bound-method-as-value)
- defaults should be able to reference earlier parameters (interpreter already supports this for functions)

## Starting point
As of the previous journal entry today:
- LLVM: closure capture discovery includes default expressions, and method defaults work when calling a **bound method value** (`obj.method` then `f()`).
- Coverage guardrails are green (`scripts/coverage_guardrails.sh`).

## Next hypotheses / risks
1) Direct method calls like `A(5).get()` likely still fail to compile when a default references `masel` because the call-site default compilation doesn’t bind `masel`.
2) Function defaults referencing earlier params (e.g. `dae f(a, b=a)`) likely fail in LLVM because defaults are compiled at the call site without bindings for parameter names.

## Plan (this session)
1) Add focused LLVM tests that reproduce (1) and (2).
2) Fix LLVM codegen to bind `masel` when compiling method defaults for *all* method call sites.
3) Decide how to support defaults referencing earlier params in LLVM:
   - likely by temporarily binding param names while compiling default expressions (call-site emulation of callee env)
4) Re-run targeted tests + coverage guardrails.
