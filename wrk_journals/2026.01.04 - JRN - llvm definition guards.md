# 2026.01.04 - JRN - llvm definition guards

## Context
- While doing core-language exploratory testing, I hit a semantic mismatch between the interpreter and the LLVM backend:
  - Interpreter: calling a function/class before its `dae`/`kin` statement executes errors (“hasnae been defined yet”).
  - LLVM/native: calls/instantiations succeeded due to hoisting/pre-registration.
  - LLVM/native also allowed forward superclasses (`kin B fae A {}` before `kin A {}`), which the interpreter rejects.

## Decision
- Keep interpreter semantics as the reference.
- Teach the LLVM backend to enforce “defined before use” at **runtime** (not compile-time), so code that only hits a forward reference on some runtime path can still compile but will error when executed (matching interpreter behavior).

## Changes (LLVM backend)
- Added per-symbol runtime “defined” guards:
  - `src/llvm/codegen.rs`
    - Per-function/constructor flags (`function_defined_flags`: `llvm_name -> i1 global`).
    - Per-class flags (`class_defined_flags`: `class_name -> i1 global`).
    - Helper emitters:
      - `guard_defined_flag(...)`, `guard_global_defined_flag(...)` (emit branch + `__mdh_key_not_found(...)` + `unreachable`)
      - `mark_global_defined_flag(...)` (store `true`)
- Mark definitions at the **statement position**:
  - `Stmt::Function`: after compiling the body, emit `fn_defined = true`.
  - `Stmt::Struct`: after compiling ctor, emit `fn_defined = true`.
  - `Stmt::Class`: emit superclass-defined guard (if any), compile class, then emit `class_defined = true`.
- Guard “use before definition”:
  - Direct calls via `compile_user_function_call(...)` now guard on the callee function’s defined flag.
  - `compile_class_instantiation(...)` now guards the class defined flag.
  - `Expr::Variable` referencing a function value now guards the function defined flag.
- Module init execution:
  - `compile_module_init_body(...)` now marks `dae`/`thing`/`kin` as defined when encountered (instead of skipping them entirely).
  - Module `kin` statements also guard that their superclass has been defined already (matches interpreter).

## Tests added
- `tests/llvm_definition_guards.rs`
  - Function call before definition errors.
  - Class instantiation before definition errors.
  - Forward superclass errors.
  - Imported module calling a function before its definition errors during import/init.

## Validation
- `timeout 2400 bash scripts/coverage_guardrails.sh` ✅
  - Functions: 100%
  - Instantiations: 100%
  - Hotspot invariant OK: interpreter missed regions `148` <= codegen missed regions `459`

## Next
- Continue exploratory testing with slightly larger “real-ish” programs to ensure these guards don’t introduce surprising order-of-evaluation changes (guards are inserted before argument evaluation for direct calls/instantiation).
- Consider whether we should also guard other hoisted constructs the LLVM backend predeclares during imports (if any remaining cases produce interpreter/LLVM mismatches).
