# Journal: LLVM function-value defaults + safe calling (2026-01-04)

## Goal
Bring the LLVM backend closer to interpreter behavior (and keep IR valid) for:
- calling named functions via first-class function values
- calling nested/captured functions that have default parameters
- ensuring function/closure calls don’t rely on mismatched indirect-call prototypes

## Repro / Symptoms
New parity tests showed two failures:
- Calling a named function through a function value did not apply defaults and could pass garbage for missing args.
- Calling a captured nested function with a default parameter returned `naething` instead of using the default.

Repro:
- `timeout 900 cargo test --features llvm --test llvm_function_value_defaults`

## Changes

### 1) Store defaults for nested functions
`function_defaults` was only populated reliably for top-level functions and methods. Nested functions weren’t storing their defaults, so call-site substitution couldn’t work.

- Updated `Stmt::Function` handling in `compile_stmt` to record defaults for every function definition encountered (including nested functions).

### 2) Fix default indexing with captures
`compile_user_function_call` prepends captures (captures-first convention), but defaults are stored for **user parameters only**. The default-filling loop was indexing defaults with the post-capture arg index.

- Adjusted default indexing to subtract the capture count (`user_idx = i - capture_count`).

### 3) Make `call_function_value` arity-safe + default-aware
The old `ValueTag::Function` path performed an indirect call using a function type based on the *provided* arg count, which is unsafe when the underlying function expects more args (defaults, etc.).

- Reworked `call_function_value` to dispatch based on the stored function-pointer payload and call the matching LLVM function directly with the correct signature.
- When fewer args are provided than the callee expects, fill missing params from defaults (or `naething`).
- Truncate extra args to keep calls well-typed in LLVM IR.

### 4) Fix regression: bound method values (`obj.method`)
`obj.method` is compiled as a closure capturing `masel`, but method functions aren’t tracked in `function_captures`. The initial closure-dispatch rewrite only considered `function_captures` keys, so bound methods became “unknown closures”.

- Extended closure dispatch to also consider method functions from `class_methods`.
- For bound methods, treat captures as `["masel"]` for default-eval binding.
