### 2026-01-02 — `len(string)` + padding semantics (codepoints)
**Decision**
- `len(string)` now returns **codepoint count** (not UTF-8 byte length).
- Width-based string ops (`pad_left`, `pad_right`, `center`, `sporran_fill`) interpret `width` in **codepoints**.
- Fill strings repeat the **first codepoint** (not the first byte).
- Empty fill string defaults to space.

**Implementation**
- Interpreter:
  - `len()` now uses `s.chars().count()` for strings.
  - `pad_left` / `pad_right` / `center` now accept **2–3 args** (fill defaults to `" "`), and measure string length in codepoints.
  - `sporran_fill` now measures string length in codepoints.
  - `clype` string “characters” count now uses codepoints.
- Native runtime (`runtime/mdh_runtime.c`):
  - `__mdh_len` / `__mdh_str_len` now return codepoint counts for strings.
  - `__mdh_center`, `__mdh_leftpad`, `__mdh_rightpad`, `__mdh_sporran_fill` now use codepoint width semantics and repeat the first UTF-8 codepoint of the fill string (empty → space).
- LLVM backend:
  - `len(string)` now calls runtime `__mdh_str_len` instead of `strlen`.
  - `pad_left` / `pad_right` / `pad` now call runtime `__mdh_leftpad` / `__mdh_rightpad` (so Unicode fill strings are safe and consistent).
  - Removed now-dead `inline_pad` (it became uncovered and broke coverage guardrails).

### 2026-01-02 — `lines(str)` vs `read_lines(path)` parity + stricter parsing
**Issues**
- Native `lines(x)` read a file and returned file lines, while interpreter `lines(str)` splits a string into lines. Interpreter `read_lines(path)` already exists for file I/O.
- Native `read_lines(path)` was an alias for `lines`, so the mismatch was structural (not just an alias bug).
- Native `date_parse` accepted trailing whitespace, while interpreter `date_parse` rejects it.
- Native runtime still used libc `isspace` in a few places (locale-dependent on bytes).

**Fix**
- Native runtime `lines(str)` now splits the **string** into lines (CRLF-safe: strips `'\r'` before `'\n'`).
- Native `read_lines(path)` now compiles as `slurp(path)` then `lines(content)` (so file I/O stays available and matches interpreter).
- Native `date_parse` no longer skips trailing whitespace (rejects any trailing text).
- Removed remaining libc `isspace` usage from `tae_int`/`tae_float` string conversions (replaced with ASCII checks).

### 2026-01-02 — `split(str, "")` semantics + native split stability
**Issue**
- Interpreter `split(str, delim)` used Rust `str::split`, where `delim == ""` yields a “split into characters” style result (with leading/trailing empties).
- Native backend special-cased empty delimiters, but its empty-delimiter path corrupted list memory (could crash under `join`), and the multi-byte delimiter path used a different list storage strategy than the rest of the native runtime.

**Decision**
- `split(str, "")` returns a single-element list `[str]` (native behavior + avoids odd empty-delimiter semantics).

**Fix**
- Interpreter: `split(str, "")` now returns `[str]`.
- LLVM native backend: `inline_split` now builds results using runtime `make_list` + `list_push` for the empty delimiter case and the multi-byte delimiter case (so the resulting list works with `join`, `len`, etc.).

**Tests**

### 2026-01-02 — `heid` / `tail` / `bum` string support + empty list safety (LLVM parity)
**Issue**
- LLVM native backend compiled `heid`/`tail`/`bum` as list-only operations (no tag checks), so calling them on strings could misinterpret string pointers as lists.
- Empty list cases could underflow indices (e.g. `tail([])`), risking crashes instead of catchable errors / defined behavior.

**Fix**
- LLVM codegen now tag-checks `heid`/`tail`/`bum`:
  - `heid(string)` -> `char_at(str, 0)` (codepoint-aware via runtime)
  - `bum(string)` -> `char_at(str, -1)` (codepoint-aware via runtime)
  - `tail(string)` -> `substring(str, 1, len(str))` (codepoint-aware via runtime)
  - `heid([])` / `bum([])` now `hurl` (catchable) instead of risking invalid loads.
  - `tail([])` returns an empty list (no underflow).

**Tests**
- Added golden regression:
  - `tests/golden/edge_cases/heid_tail_bum_string_and_empty_list_parity.*`

### 2026-01-02 — `scran` negative/float indices + `yank` empty-list safety (parity + crash-proofing)
**Issues**
- Interpreter `scran(x, start, end)`:
  - ignored negative indices for lists/strings, diverging from native behavior,
  - could panic on `start > end` (slice range underflow).
- LLVM native `scran(x, start, end)` did not coerce float indices to ints (unlike interpreter), which could produce incorrect slices or runtime type errors.
- LLVM native `yank(list)` had no tag/empty-list checks, risking underflow/crash on `yank([])` and UB-like behavior on `yank(non_list)`.

**Fix**
- Interpreter `scran` now:
  - supports negative indices consistently (like `substring` / runtime slice semantics),
  - clamps/normalizes `start/end` so `start >= end` yields an empty slice (no panic).
- LLVM codegen:
  - `scran(..., start, end)` now coerces `start/end` via `coerce_i64` (int/float) before slicing.
  - `yank` now tag-checks for list and `hurl`s on empty list (catchable), rather than underflowing.
  - Removed the now-unused byte-based `inline_char_at` helper (it was only used by a previous `scran(string)` implementation and was not UTF‑8 safe).

**Tests**
- Added golden regressions:
  - `tests/golden/edge_cases/scran_negative_and_float_indices_parity.*`

### 2026-01-02 — `tak` / `drap` negative + float `n` parity (list ops)
**Issues**
- Interpreter `tak/drap` only accepted `integer` `n` and used `as usize` casts:
  - negative values could turn into huge `usize` and produce surprising results.
- Native `tak` runtime clamps negative `n` to 0, but `drap` codegen used an unsafe `inline_scran` slice path with no normalization, risking underflow for negative `n` and diverging from interpreter.
- Native `tak/drap` did not coerce float `n` consistently with other index-y builtins.

**Fix**
- Interpreter:
  - `tak`/`drap` now accept `int/float` via `as_integer()` and clamp negative `n` to 0.
- LLVM codegen:
  - `tak` now type-checks `list` and coerces `n` via `coerce_i64` before calling runtime `__mdh_tak`.
  - `drap` now type-checks `list`, coerces `n` via `coerce_i64`, clamps negative `n` to 0, and uses runtime `list_slice` instead of the unsafe `inline_scran` path.

**Tests**
- Added golden regression:
