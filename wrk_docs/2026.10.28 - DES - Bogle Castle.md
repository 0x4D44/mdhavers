# Bogle Castle: a Doom-style engine in mdhavers (design)

**Date:** 2026-10-28
**Baseline:** `origin/master` at `d328d43` (DEC round 7)
**Decisions it implements:** DEC round 7 (showcase, native graphics bridge, no external
dependencies, own assets, headless parity testing) and Arthur's brief for this doc (Codex-generated
PNG art, Scottish haunted-castle theme).
**Status:** design only. The only code written is the measurement probes in section 3, which are
not committed.

Fact, inference and guess are marked where it matters. "Measured" means observed on this machine
(FLUX, Apple M5 Max) in this session.

---

## 0. Summary of the choices

| Area | Choice |
|---|---|
| Renderer | **Portal renderer over convex sectors** (Build-engine style), no BSP and no preprocessing. |
| Maths | **16.16 fixed point in mdhavers integers** (i64); no floats in the engine core. Angles are integers (0..4095). Trig from a committed integer table. |
| Pixels | **8-bit indexed** 320x200 framebuffer in a `bytes` object; 256-colour palette plus 32 light-level colour maps, as Doom. |
| Presentation | Bridge converts indexed to BGRA in C and scales up (integer factor, nearest neighbour). |
| Bridge | `screen_open`, `screen_shaw`, `screen_should_close`, `screen_close`, `key_down`, `key_pressed`, `mouse_x`, `mouse_y`, `mouse_dx`, `mouse_dy`, `mouse_down`, `screen_grab_mouse`; time from the existing `mono_ns`/`mono_ms`/`snooze`. |
| macOS layer | Pure C through `objc_msgSend`; `CALayer.contents = CGImage`; a manual event pump; no Objective-C compiler and no NSView subclass. |
| Linking | AppKit/QuartzCore/CoreGraphics/libobjc are linked **only when codegen saw a bridge call**. |
| Assets | Codex PNGs committed as source art; an offline **baker** in mdhavers (PNG decoder + quantiser to the fixed palette) writes raw `.bog` files the game loads. |
| Gameplay v1 | Comic Scottish: weapons sgian-dubh, deep-fried Mars bars (thrown arc, splash), blunderbuss, **bagpipes** (signature: fill the bag, then a stunning, knockback cone blast that disperses midges); enemies gamekeeper (charger), exploding haggis (kamikaze), tartan ghost (floats through walls), midge swarm (damage cloud); kelpie, bogle and the Piper's Ghost later. |
| Testing | Engine core is pure (`tic`, `render` into bytes); headless runner replays input and prints FNV-1a frame hashes; interpreter and native must print the same hashes at 80x50. |

## 1. Engine design

### 1.1 Map representation

All coordinates are integer map units (1 unit is about 1/64 of a 64-texel wall; the player is 56
units tall, as Doom). Stored as plain mdhavers lists of integers (struct-of-arrays) for speed: a
dict per wall would cost a hash lookup per field access.

- **Vertices:** `vx[i]`, `vy[i]`.
- **Sectors:** a **convex** polygon, vertices listed counter-clockwise, plus `floor_h`, `ceil_h`,
  `floor_tex`, `ceil_tex` (or sky), `light` (0..255), `tag`, `kind` (normal, door, water, damage,
  exit).
- **Walls:** each sector owns a run of walls `wall_first[s] .. wall_first[s] + wall_count[s]`.
  A wall goes from its vertex to the next one in the loop and has `portal` (neighbour sector or
  -1), `upper_tex`, `lower_tex`, `mid_tex`, `x_off`, `y_off`, `flags` (unpegged, blocking).
- **Portals:** a wall with `portal >= 0` is open. The map builder pairs the two directed copies of
  each shared edge and checks they match exactly.
- **Things:** `type`, `x`, `y`, `z`, `angle`, `sector`, `state`, `tics`, `health`, flags.

Rooms that are not convex are split by the map builder into convex sectors joined by portals with
identical heights (invisible joins). The engine never sees a concave sector.

### 1.2 Renderer: portal rendering (recommended) over Doom's BSP

**Recommendation: Build-style portal rendering over convex sectors, front to back, with
per-column clip windows.** Reasons:

1. **No BSP builder.** A Doom node builder (partition choice, seg splitting, robust integer
   intersection, slime trails) is the hardest offline tool in the Doom tool chain and adds a whole
   stage of work and bugs; the map builder would have to run it after every edit.
2. **Front-to-back for free.** In a convex sector no wall facing the viewer hides another wall of
   the same sector, so walls need no sorting. Crossing a portal only shrinks the visible column
   range, so the traversal is front to back by construction.
3. **Dynamic heights.** Doors and lifts only change `ceil_h`/`floor_h`; nothing is precomputed.
4. **Small.** The core is about 300 lines of mdhavers (estimate).

What we give up: Doom's guaranteed "each wall pixel drawn once" ordering is replaced by the
convexity rule, so the map builder must enforce convexity (a cheap check). The Freedoom WAD
stretch goal needs WAD subsectors turned into convex sectors (section 7, stage 7).

**Algorithm, per frame:**

1. `ytop[x] = 0`, `ybot[x] = H-1` for every screen column.
2. Queue `(player_sector, x0 = 0, x1 = W-1)`; a visited-count per sector caps re-entry (32 entries
   in flight max).
3. Pop `(s, x0, x1)`. For each wall of `s`: transform both ends to view space (integer rotate by
   the view angle using the trig table), drop it if both ends are behind the near plane, clip it
   against the near plane (z = 1/4 unit, fixed point), project to screen x (`x = W/2 + xv * focal
   / z`), drop it if back-facing or outside `[x0, x1]`.
4. For each screen column `x` in the wall's clipped range, interpolate `1/z` linearly in screen
   space (exact for perspective), derive `z`, the wall top/bottom rows, and the texture `u`
   (from `u/z`, also linear in screen space; one division per column):
   - ceiling span `ytop[x] .. top-1` of `s`'s ceiling, floor span `bottom+1 .. ybot[x]` of its
     floor (section 1.4);
   - one-sided wall: draw the mid texture `top..bottom`, then close the column
     (`ytop[x] = H`, `ybot[x] = -1`);
   - portal: draw the upper wall (neighbour's ceiling lower than ours) and lower wall (neighbour's
     floor higher), then narrow `ytop[x]`, `ybot[x]` to the opening.
   - record a **drawseg** (x range, z per column end, the clip rows after this wall) for sprite
     clipping.
5. Push `(neighbour, max(x0, wx0), min(x1, wx1))` for each portal wall with a non-empty range.
6. Stop when the queue is empty or every column is closed.

**Wall columns:** texture column `u mod 64`, vertical step `dv = (tex_h << 16) / screen_h` in
16.16, start `v` from the clipped top. Inner loop per pixel: texel read, colour-map read, frame
write, `v += dv`. This is exactly the probe in section 3.

### 1.3 Clipping

- **Near plane** in view space (3D clip of each wall segment, integer).
- **Horizontal:** by the portal window `[x0, x1]` carried in the queue.
- **Vertical:** by `ytop[x]`/`ybot[x]`, so a step or lintel seen through a portal is cut
  correctly.
- **Sprites:** by drawsegs (as Doom's `R_DrawSprite`): for each sprite column, every drawseg
  nearer than the sprite that covers that column clips it to its recorded opening.

### 1.4 Floors and ceilings

Two options, same output:

- **(a) Per-column ("vertical") flats.** For each pixel row `y` of a floor span, distance
  `d = (eye_z - floor_h) * rowscale[y]` (a per-frame table of `focal / (y - horizon)`), world
  `(u, v) = view_pos + d * ray_dir[x]`. Two multiplies per pixel more than a wall pixel.
- **(b) Doom visplanes.** Record per plane (height, texture, light) the `top[x]`/`bottom[x]` per
  column, then convert to horizontal runs (`R_MakeSpans`); each row has one distance, so the inner
  loop is two adds per pixel.

**Recommendation:** (a) first: it is about half the code and it sits inside the column walk.
Switch to (b) in stage 3 only if the frame budget (section 3) needs it. Sky ceilings draw a
cylinder-mapped sky column (texture column from the view angle, no distance).

### 1.5 Lighting

Doom's model. 32 colour maps of 256 bytes (`cmap[level * 256 + colour]`, map 0 brightest).
Light level per pixel = sector light (0..255, quantised to 32 steps) minus a distance term
(`min(31, base + z >> k)`), clamped. Walls use one level per column; flats one per row (b) or per
pixel (a, from `d`). One table read per pixel. Full-bright sprite frames (wisps, torches) skip the
map. Colour map 32 (extra) is the "invulnerable/hurt" tint, defer.

### 1.6 Sprites

Things in sectors visited this frame are collected during the traversal. Project each one (view
`z`, screen `x` centre, scale = focal / z), drop the far ones, sort far to near (insertion sort;
fewer than 64 visible), draw column by column, clipped by drawsegs (1.3) and the screen, with
index 255 transparent. One sprite view per thing in v1 (always faces the player); rotations
later. Light: the thing's sector light with the distance term.

### 1.7 Collision and movement

35 tics per second, as Doom; all game logic runs per tic in fixed point.

- **Body:** circle of radius 16 (player) or per type; height 56.
- **Move:** try `pos + vel`. For each wall of the current sector and of every sector the circle
  overlaps (found by walking portals within the radius), the wall blocks if it is one-sided, or
  the step up is more than 24 units, or the opening (`min ceil - max floor`) is under the body
  height. On a block, remove the velocity component along the wall normal and retry once
  (slide).
- **Sector tracking:** after a move, if the centre crossed a portal wall (sign of the edge's
  cross product changed), move to that neighbour. Convexity makes the point-in-sector test one
  cross product per wall.
- **Height:** `z` snaps to the floor when walking; view height eases up steps (Doom's
  `deltaviewheight`); gravity when falling.
- **Hitscan/sight:** a 2D ray walked through portals, checking the vertical opening at each
  crossed wall; used for weapons and monster line of sight.
- **Doors:** sectors whose ceiling moves between floor and the lowest neighbour ceiling minus 4.

### 1.8 Maths: fixed point, and why the frames are bit-identical

**All engine-core arithmetic is on integers.** Positions and heights in 16.16 (`FRAC = 65536`),
angles 0..4095 (12-bit "BAM"), products formed as `a * b / 65536` in i64 (no overflow: map
coordinates stay below 2^15 units, so `a, b < 2^31` and `a*b < 2^62`).

Why this is bit-identical between the interpreter and native (fact, from the code):

- Interpreter: `i64` with `checked_*`; `/` is Rust's truncating division
  (`src/interpreter.rs:12714`), `%` is truncating remainder. Native: LLVM `sdiv`/`srem` on i64,
  also truncating. Integer results therefore agree exactly whenever neither side errors.
- Overflow: the interpreter raises `IntegerOverflow`; native must raise too, or at least never be
  reached. The bounds above keep every product under 2^62; a unit test drives the extremes.
- Division by zero raises in both; the engine guards every divide (`z` is clamped to >= 1/4 unit
  at the near plane).
- Trig: `sin_tab[4096]` (and `cos` as `sin_tab[(a + 1024) % 4096]`), 16.16 values, plus
  `tan`/`atan` tables, **generated once and committed** as a text table (`data/trig.txt`), not
  computed with `sin()` at start-up. Fact: both backends call the platform libm today, so they
  would agree on one machine, but committed tables make the golden hashes portable to Windows
  and Linux too.
- **No floats in the engine core.** A float anywhere would still be IEEE-exact for `+ - * /`
  (LLVM emits no fused multiply-add without fast-math flags, and Rust does not fuse either), but
  int-to-float-to-int conversions and libm calls are where backends drift. A unit test greps the
  engine sources for float literals and float builtins (`sqrt`, `sin`, `floor`, ...).
- `sqrt` (for distances in AI) is an integer square root in mdhavers.
- Negative division rounds towards zero, unlike Doom's arithmetic shifts. That is fine as long as
  both backends agree, which they do; the engine uses `/` everywhere, never `bit_shove_right`, so
  there is one rounding rule.

The parity test (section 6) is the check that this holds in practice.

### 1.9 Resolution

**320x200 internal**, square pixels (16:10, like most Mac displays), 8-bit indexed. The bridge
scales by the largest integer factor that fits 85% of the screen (x4 = 1280x800 on a laptop),
nearest-neighbour. The engine takes `W` and `H` as parameters (every table is built from them),
so headless tests run at 80x50 and a later "high detail" mode could run 640x400 if the budget
allows. Field of view 90 degrees horizontally, `focal = W / 2`.

## 2. The framebuffer bridge

### 2.1 Names and signatures

The names reuse the interpreter's existing graphics vocabulary (`screen_*`, `key_*`, `mouse_*`,
`src/graphics.rs`) so a program reads the same on either backend. New names are marked.

| Name | Args | Returns | Meaning |
|---|---|---|---|
| `screen_open(w, h, title)` | int, int, string | naething | Open a window showing a `w` x `h` logical framebuffer, scaled up. Hurls if one is open. |
| `screen_shaw(pixels, palette)` **new** | bytes `w*h`, bytes 768 | naething | Present a frame: `pixels` are palette indices, `palette` is 256 RGB triples. With `palette = naething`, `pixels` must be `w*h*4` bytes BGRA. Pumps pending events. Never blocks for vsync. |
| `screen_should_close()` | | aye/nae | Pumps events; aye once the window's close button, Cmd-Q or Alt-F4 was used. |
| `screen_close()` | | naething | Close the window (no-op if none). |
| `screen_width()`, `screen_height()` | | int | Logical size. |
| `key_down(name)` | string | aye/nae | Key is held. Names as `graphics.rs` (`"a"`..`"z"`, `"up"`, `"space"`, `"escape"`, ...) plus `"0"`..`"9"`, `"shift"`, `"ctrl"`, `"alt"`, `"tab"`. |
| `key_pressed(name)` | string | aye/nae | Key went down between the previous two `screen_shaw` calls (edge, per frame). |
| `mouse_x()`, `mouse_y()` | | int | Pointer in logical pixels. |
| `mouse_dx()`, `mouse_dy()` **new** | | int | Raw motion since the previous frame (works while grabbed). |
| `mouse_down(button)` **new** | int (0 left, 1 right, 2 middle) | aye/nae | Button held. (The interpreter's `mouse_pressed` stays as the edge test.) |
| `screen_grab_mouse(on)` **new** | aye/nae | naething | Hide the cursor and decouple it from the mouse, for turning. |
| `mono_ns()`, `mono_ms()`, `snooze(ms)` | existing | | Time and sleep, already in both backends. |

Native code keeps the existing "Nae windae!" hurl for `draw_*`, `screen_clear` and friends:
all drawing is in mdhavers.

### 2.2 Pixel buffer ownership

- The framebuffer is an ordinary mdhavers `bytes` object, owned by the program.
  `MdhBytes { uint8_t *data; int64_t length; int64_t capacity; }` (`runtime/mdh_runtime.h:66`)
  already keeps its payload in a separate buffer, so C reads `data` directly: **no copy across
  the boundary**.
- The bridge **borrows** the buffer for the duration of `screen_shaw` only and never keeps the
  pointer (safe under reference counting, safe if the program resizes it later). It checks the
  tag and `length == w*h` (or `w*h*4`) and hurls in Scots otherwise.
- Inside `screen_shaw` C converts indices to BGRA through the palette into one of two
  bridge-owned buffers (256 KB each at 320x200), wraps that in a `CGImage` and hands it to the
  layer. Measured cost of that loop: section 3 (it is C, about 3 instructions a pixel).
- The interpreter borrows `Rc<RefCell<Vec<u8>>>` the same way.

### 2.3 Event model and frame pacing

- **Polling, no callbacks.** mdhavers natives cannot call user code (HLD 4.4), and a poll API
  is the same in all backends. `screen_shaw` and `screen_should_close` drain the OS queue
  without blocking and update a key-state table, an edge table (reset at each `screen_shaw`),
  mouse position and accumulated motion.
- **Pacing in mdhavers:** the game runs fixed 35 Hz tics from a `mono_ns` accumulator, renders
  once per loop, and calls `snooze(1)` when it is ahead. Rendering faster than the display is
  harmless (the layer shows the latest image). No vsync wait in v1; if tearing shows, pace
  by sleeping to the next 1/60 s (open question 4).

### 2.4 What the interpreter does with these names

- **`graphics` feature on (default `full`):** implement `screen_shaw`, `mouse_dx/dy`,
  `mouse_down`, `screen_grab_mouse` on the existing raylib window (`screen_shaw` converts to RGBA
  and updates one raylib texture drawn scaled). About 120 lines in `src/graphics.rs`. Lets the
  game be debugged in the interpreter at low resolution. DEC round 7 says the interpreter's
  raylib graphics are "untouched for now": this adds names and changes none (open question 1).
- **`graphics` off (`cli`, `minimal`, the playground):** the names exist and hurl the same
  "Nae windae!" error native code uses today.
- **Headless runs never call the bridge** (section 6), so parity tests need neither.

### 2.5 C layer per OS

Files: `runtime/platform/mdh_screen.h` (internal API: `mdh_scr_open/present/pump/close`),
`runtime/mdh_screen.c` (the `__mdh_screen_*` builtins: argument checks, key tables, palette
conversion, Scots errors), `runtime/platform/screen_macos.c`, `screen_win32.c`, `screen_none.c`
(Linux until X11: "Nae windae on this platform yet").

**macOS (in detail).** C only, compiled by the existing `cc` crate step; no `.m` files.

- Includes `<objc/runtime.h>`, `<objc/message.h>`, `<CoreGraphics/CoreGraphics.h>`; AppKit
  constants are `#define`d locally (no AppKit headers needed; they are Objective-C).
- Messages are sent through `objc_msgSend` cast to the exact C function type of each call
  (`((id (*)(id, SEL, CGRect, NSUInteger, NSUInteger, BOOL))objc_msgSend)(...)`). On arm64 there
  is no `_stret` variant, and struct arguments (`CGRect`) go in registers by the cast. Intel Macs
  would need `objc_msgSend_stret` for the one struct return we use (`frame`); arm64 only for now.
- **Open:** `[NSApplication sharedApplication]`, `setActivationPolicy:Regular`, build a minimal
  main menu with Quit (Cmd-Q), `[[NSWindow alloc] initWithContentRect:styleMask:backing:defer:]`
  with titled, closable, miniaturizable; `setTitle:` from an `NSString` made with
  `stringWithUTF8String:`; `contentView setWantsLayer:YES`; layer `setMagnificationFilter:`
  `kCAFilterNearest` (the string constant loaded with `dlsym`), `makeKeyAndOrderFront:`,
  `activateIgnoringOtherApps:YES`, `finishLaunching`. Every call runs in an autorelease pool
  pushed with `objc_autoreleasePoolPush/Pop`.
- **Present:** `CGDataProviderCreateWithData` over the current BGRA buffer, `CGImageCreate`
  (8 bpc, 32 bpp, `kCGImageAlphaNoneSkipFirst | kCGBitmapByteOrder32Little`, sRGB colour space),
  `[layer setContents:image]` inside a `CATransaction` with actions disabled, release the image,
  flip buffers.
- **Pump:** loop `nextEventMatchingMask:NSEventMaskAny untilDate:[NSDate distantPast]
  inMode:NSDefaultRunLoopMode dequeue:YES`; read `type`, `keyCode`, `modifierFlags`, `deltaX/Y`,
  `locationInWindow` from each event; key events are consumed (not forwarded, so no system beep
  and no key repeat), everything else goes to `sendEvent:`. Then `updateWindows`.
- **Close detection:** a window-delegate class made at run time with `objc_allocateClassPair` and
  `class_addMethod` for `windowWillClose:` and `applicationShouldTerminate:` (sets a flag), so no
  Objective-C compiler is needed.
- **Mouse grab:** `CGAssociateMouseAndMouseCursorPosition(false)` + `[NSCursor hide]`; deltas
  from `deltaX/Y` of mouse-moved events.
- **Thread:** AppKit must run on the main thread. Native `main` is the process main thread
  (fact: codegen adds `main`, `src/llvm/codegen.rs:5158`); threads spawned by the program must not
  call the bridge (it hurls if `pthread_main_np() == 0`).

**Windows (outline).** `RegisterClassW` + `CreateWindowExW`; `PeekMessageW` loop in the pump;
`WM_KEYDOWN/UP`, `WM_CLOSE`; raw input (`RegisterRawInputDevices`) for mouse deltas,
`ClipCursor` + `ShowCursor(FALSE)` for the grab; present with `StretchDIBits` from a
`BITMAPINFO` with an **8-bit DIB and a 256-entry colour table**, so GDI does the palette
conversion and scaling itself; time is already in the platform layer. Win64 ABI caveat: the
bridge takes `MdhValue` by value like every runtime call, so it inherits whatever fix lands for
the Win64 struct-passing gap (HLD 7.2).

### 2.6 Linking only when used

- The bridge objects are a separate archive, `mdh_screen.a`, built by `build.rs` beside the
  runtime archives and embedded the same way (`include_bytes!`, `build.rs:98`).
- `CodeGen` sets `uses_screen = true` when it compiles a call to any bridge name.
- `link_native_executable_from_object` (`src/llvm/compiler.rs:398`) then adds `mdh_screen.a` and, on macOS,
  `-framework AppKit -framework QuartzCore -framework CoreGraphics -lobjc`; on Windows
  `-luser32 -lgdi32`. Programs that never call the bridge link exactly as today.

## 3. Performance budget (measured)

**Method.** Instruction and cycle counts from `/usr/bin/time -l` ("instructions retired",
"cycles elapsed"), not wall-clock time (perf runs are banned on the shared FLUX until
2026-10-29 17:30). Release build of this worktree (`cli,llvm,native`, `-O2` default), RC off and
`MDH_RC=1`. Each probe was built at 0, 1 and 20 frames; per frame = (20-frame count - 1-frame
count) / 19, which removes start-up and set-up. The probe sources are kept out of the commit
(listed below so they can be rebuilt).

- **fill:** 320x200 indexed framebuffer, one `bytes_set(fb, i, (i + f) % 256)` per pixel in a
  `whiles` loop.
- **wall:** the inner loop of 1.2: 320 columns per frame, one `draw_col` call per column (8
  arguments), per pixel one texel `bytes_get`, one colour-map `bytes_get`, one `bytes_set`, a
  16.16 step and a `/ 65536 % 64`. Column heights vary 1..199, average 98.5 pixels
  (31,514 pixels per frame).
- **conv:** the bridge's C palette conversion (`out[i] = pal[px[i]]`, 64,000 pixels), `cc -O2`.

**Results (measured):**

| Probe | Backend | Instructions / frame | Instructions / pixel | Cycles / frame | IPC |
|---|---|---:|---:|---:|---:|
| fill | native, RC off | 3.32 M | 52 | 0.52 M | 6.4 |
| fill | native, RC on | 3.16 M | 49 | 0.68 M | 4.6 |
| wall | native, RC off | 7.52 M | 239 | 1.24 M | 6.1 |
| wall | native, RC on | 8.86 M | 281 (+18%) | 1.36 M | 6.5 |
| fill | interpreter | 477 M | 7,460 | 100 M | 4.8 |
| wall | interpreter | 568 M | 18,000 | 132 M | 4.3 |
| conv | C (bridge) | 0.21 M | 3.3 | 0.06 M | 3.5 |

(The fill RC-on figure being lower than RC off is within run-to-run noise of the subtraction; the
wall figure is a real +18%, from retain/release of the three `bytes` arguments per column call
and per-pixel temporaries.)

**Instruction rate for this machine.** IPC is measured above (about 6 on these native loops;
note the count is of cycles the thread actually ran, so it is not distorted by the box's load).
The clock is not exposed by `sysctl` on Apple Silicon; **assumed 4.0 GHz** for an M5 Max
performance core (a conservative guess below the about 4.5 GHz Apple's M4-generation P-cores
run at; not measured). That gives **about 24 G instructions/s** for native engine code. A
pessimistic floor, if IPC collapses to 1 on real code with cache misses: **4 G/s**.

**Frame budget at 320x200 (inference from the measurements):**

| Item | Estimate |
|---|---:|
| Walls + floors + ceilings: every pixel drawn once, about 260 instructions (wall 239; flats per 1.4 (a) a little more) | 17 M |
| Sprites and overdraw (about +20%) | 3.5 M |
| Column set-up, portal traversal, game tic, colour conversion in C | 2 M |
| **Total** | **about 23 M instructions/frame** |

- Native at 24 G/s: **about 1,000 frames/s**; at the pessimistic 4 G/s: **about 170 frames/s**.
  The game needs 35 tics/s and 60 frames/s. **Native is fast enough with no language changes**,
  with at least 3x headroom even pessimistically, and even 640x400 (4x the pixels) would hold
  about 40 frames/s at the pessimistic rate. RC on (+18%) does not change the conclusion.
- Interpreter: about 75x slower per pixel (18,000 vs 239). A 320x200 frame is about 1.2 G
  instructions: 3-20 frames/s, so interpreter play is a debugging aid at 160x100 at best.
  **Headless parity at 80x50** (4,000 pixels) costs about 75 M instructions a frame, so 10
  hashed frames plus 350 tics of game logic stay well under a few seconds.

**Optional work items (not needed for v1; separate lanes if wanted):**

1. **Inline `bytes_get`/`bytes_set` in codegen** (tag check, bounds check, load/store; call the
   runtime only on the slow path). Today each is a runtime call with type checks; this is most of
   the 239 instructions a pixel. Guess: 3-5x fewer instructions a pixel.
2. **RC borrowing for `bytes` arguments** of user functions (the R7 borrowing redesign already
   planned would cover it): removes the +18%.
3. **Interpreter fast path for integer locals and `bytes` builtins** if interpreter play at
   160x100 is wanted; not needed for the parity tests.

**Probe sources** (for re-running): `fill.tmpl` and `wall.tmpl` as described above with
`FRAMES` substituted; built with `mdhavers build x.braw -o x` (and `MDH_RC=1`), run with
`deltic timeout 300 /usr/bin/time -l ./x </dev/null`.

## 4. Assets

### 4.1 Palette and textures

**Recommendation: 256-colour palette with 32 light-level colour maps (Doom's model), not true
colour.** Reasons: one byte per pixel matches `bytes` (a true-colour pixel is four
`bytes_set` calls, so four times the cost measured in section 3); lighting is one table read
(true colour needs three multiplies); the conversion to screen colours happens once per pixel in C.

- **Palette:** fixed and hand-designed, committed as `games/bogle/art/palette.txt` (256 lines of
  `r g b`): 16 ramps of 16 shades (granite greys, peat browns, moss greens, loch blues, heather
  purples, tartan reds, torch oranges, bone, skin, ghost cyan, kelpie teal, gold, ...), index 0
  black, index 255 reserved as transparent. The baker quantises every image to this palette, so
  textures from different generations still share one look.
- **Colour maps:** generated by the baker: map `k` is each colour darkened by `k/32` towards
  black, matched back to the nearest palette entry. Written as `colormap.bog` (32 x 256 bytes).
- **Sizes:** walls and flats **64x64** (power of two: `u % 64`), a few tall walls 64x128; sky
  256x128; sprites up to 64x96, frames padded to a whole column.

### 4.2 PNG subset (decoder in mdhavers)

- Signature, `IHDR`, `PLTE`, `IDAT` (concatenated), `IEND`; ancillary chunks skipped. CRC not
  checked; zlib Adler-32 checked.
- Bit depth 8; colour types 2 (RGB), 6 (RGBA), 3 (indexed), 0 (grey). No interlace (rejected
  with a Scots error).
- Inflate: stored, fixed-Huffman and dynamic-Huffman blocks (RFC 1951), canonical-code tables,
  32 KB window (all output is in one `bytes`, so back references just index it).
- Filters: None, Sub, Up, Average, Paeth.
- Runs in the **baker only**, not at game start, so the interpreter parity runs and the native
  game load raw indexed data. Fallback if the decoder becomes a time sink: `sips -s format bmp`
  plus a trivial BMP reader (Arthur's fallback, adapted: BMP is uncompressed and `sips` writes it).

### 4.3 Asset layout

```
games/bogle/
  engine/            core: fixed.braw trig.braw map.braw render.braw things.braw move.braw game.braw
  shell/main.braw    window loop (bridge calls only here)
  shell/headless.braw replay + frame hashes
  tools/bake.braw    PNG -> .bog (indexed), palette, colour maps
  tools/png.braw     inflate + PNG decoder (library)
  tools/mapbuild.braw map builder library; maps/*.braw are level scripts using it
  art/src/           Codex PNGs as generated (source art, committed)
  art/palette.txt
  data/              baked *.bog, colormap.bog, trig.txt, *.map (committed; a test checks
                     they match a fresh bake)
  replays/           recorded input for tests
```

`.bog` is `BOG1 w h` (ASCII line) then `w*h` index bytes, column-major (walls and sprites are
drawn by column).

### 4.4 Codex image-generation constraints

A shared style preamble on every prompt:

> Cartoonish comic Scottish haunted-castle style, like a hand-painted 1990s shareware game:
> chunky shapes, bold dark outlines, exaggerated friendly-spooky proportions, big readable
> silhouettes that still read at 64 pixels. Palette of granite grey, peat brown, moss green, loch
> blue and heather purple, with bright accents of tartan red, torch orange and ghost cyan. Even,
> flat, frontal lighting; no cast shadows, no vignette, no text, no signature, no border.
> Affectionate and silly, never gory.

The same preamble on every prompt, one generation session per batch, and the fixed palette at
bake time are what keep the style consistent.

- **Wall and flat textures:** "seamless tileable texture, edges wrap left-right and top-bottom,
  orthographic straight-on view, no perspective", square, then the subject (rough-hewn granite
  blocks, oak panelling with iron studs, mossy flagstones, wet dungeon brick, tapestry with a
  thistle, portcullis bars, peat-and-straw floor, slate roof underside, carved Celtic knot
  lintel, cell door). The baker box-filters the 1024-square output to 64x64 **with wrap-around**,
  so tiling survives the downscale, and shows a 3x3 tiled preview for review.
- **Sprites:** "single figure, full body, facing the viewer, centred, feet at the bottom edge,
  on a flat pure magenta #FF00FF background, no shadow on the ground". Magenta is the chroma
  key (the generator's alpha is not relied on): pixels near #FF00FF become index 255. Frames
  per monster: idle, 2 walk, attack, pain, death (4 frames); the same seed/description line for
  every frame of one monster. Subjects: a red-bearded gamekeeper in a kilt, tweed waistcoat and
  deerstalker, waving a shepherd's crook; a translucent ghost made of billowing red tartan with
  hollow eyes; a grinning haggis with stubby legs and a lit fuse; a dripping kelpie (water
  horse) with weed for a mane; a bogle (lumpy grey goblin, long arms); a cloud of midges (many
  tiny black dots, roughly round, slightly see-through: drawn as a sprite with scattered pixels
  and lots of transparency); a ghostly piper (boss) with spectral bagpipes.
- **Weapon view sprites** (bottom-centre of the screen, first person, hands visible): a hand
  holding a deep-fried Mars bar in batter; a hand with a sgian-dubh; a set of bagpipes held under
  the arm with the chanter in hand (frames: deflated, filling, full, blasting); a caber held
  upright; a hand cocking a blunderbuss.
- **Pickups and dressing:** a bright orange can and a big bottle labelled "Girder Juice" with a cartoon steel girder (a parody: no real logo, can design, colours-and-stripes pattern or the word "Irn-Bru"), a
  plate of haggis, neeps and tatties, a tin of shortbread, a tartan-wrapped key, a whisky barrel,
  a stuffed stag's head, a suit of armour with a tam o' shanter, a lit brazier, a thistle in a
  pot, a Highland cow portrait.
- **Sky:** "wide panoramic night sky over Highland hills, wraps left to right, horizon on the
  lower third".
- Review step: a human (or the lead) looks at the 3x3 tiled preview and the baked 64x64 before a
  texture is committed.

### 4.5 Map format and the first level

Maps are written as mdhavers scripts using the map-builder library (`room`, `split_convex`,
`door`, `stairs`, `thing`), which validates and writes `data/<name>.map`, a line-based text
file the engine loads:

```
BOGMAP 1
v <x> <y>                                        # vertices
s <floor_h> <ceil_h> <floor_tex> <ceil_tex> <light> <kind> <tag> <v0> <v1> ... # convex, CCW
w <sector> <index> <upper> <lower> <mid> <x_off> <y_off> <flags>   # optional wall overrides
t <type> <x> <y> <angle> <flags>                  # things
```

Portals are not written: the loader pairs shared edges. Validation (builder and loader): every
sector convex and CCW, no zero-length walls, each shared edge matched exactly once, every
sector reachable, player start inside a sector.

**E1M1 "The Gatehouse"** (about 40 sectors): moonlit courtyard (sky) with a well and a
midge-infested bog corner (damaging floor); gatehouse passage with a portcullis door and two
gamekeepers; the great hall with a raised dais (two steps), stag heads, whisky barrels and a
haggis ambush from under the banqueting table; the chippy kitchen (deep-fat fryer sector:
damaging, glowing floor, full-bright) where the deep-fried Mars bars are found; spiral stair
(8 step sectors) down to the dungeon; flooded crypt (water floor at -24, kelpie lair) holding
the iron key; tartan ghosts in the portrait gallery (iron-key door) guarding the silver key; the
bagpipes on a plinth in the chapel; silver-key door to the battlement stair; exit at the lever
on the battlements, past the piper's ghost.

## 5. Theme and gameplay scope for v1

Tone: affectionate, comic Scottish (Arthur: "have fun with it"), never mean and never gory.
Enemies burst into tartan rags, steam or crumbs, not blood. Every behaviour below is chosen to be
cheap: a handful of Doom-style states (`state, tics, next`), sight by the portal ray (1.7), and
the shared move code.

### 5.1 Player

Health 100, "spirit" (armour) 0-100, move/strafe/turn (keys and mouse), use (doors, lever),
fire, weapon select 1-5. Hurt grunts in Scots ("Ya wee scunner!").

### 5.2 Weapons (each with a distinct feel)

| # | Weapon | Feel | Mechanic (cheap) | Ammo |
|---|---|---|---|---|
| 1 | **Sgian-dubh** | quick melee | hitscan, range 64, fast | none |
| 2 | **Deep-fried Mars bars** | thrown arc, splash | projectile thing with gravity (`vz -= g` per tic), bounces once off a floor, bursts on impact: splash damage radius 64, leaves a sizzling sprite for 1 s | Mars bars (boxes of 5) |
| 3 | **Blunderbuss** | close-range spread | 7 hitscan pellets in a fan, spread from the seeded PRNG | powder and shot |
| 4 | **Bagpipes** (signature) | fill, then cone blast | section 5.3 | "puff" (refills on its own) |
| 5 | **Caber** (deferred) | slow, huge knockback | melee sweep, range 96, 1.2 s swing; knocks the target back along the view direction | none |

### 5.3 The bagpipes

- **Fill the bag:** hold fire. The view sprite inflates over 0.6 s (21 tics, three frames) and
  the drone starts (the first sound effect of stage 5). Letting go early cancels with a sad
  wheeze.
- **Blast:** when full, release (or it fires itself after 1 s): a **cone of sound**, 60 degrees
  wide, range 320. Every thing in the cone with line of sight (portal ray) takes area damage
  that falls off with distance, is **stunned** for 1.5 s (its state machine jumps to a `stunned`
  state) and is **knocked back** along the player-to-target direction (a velocity impulse, then
  the shared move code with its wall sliding). Exploding haggises in the cone go off (chain
  reactions).
- **Midges:** the blast **disperses** a midge swarm outright (5.4). It is the only weapon that
  does, which gives the bagpipes a clear job.
- **Cost:** 34 puff per blast; puff refills 1 per tic up to 100: three blasts back to back, then
  a breather.
- **Why this mechanic:** the cone test is one dot product and one distance per nearby thing;
  stun and knockback reuse existing pieces; it is good against crowds, midges and kelpies
  (push them back into the loch) without a new system.

### 5.4 Enemies

v1 ships the first four; the rest are the roster for later levels (the art batch includes them).

| Enemy | Behaviour | Why it is cheap |
|---|---|---|
| **Gamekeeper** (kilt, red beard, crook) | **Charger.** Patrols; on sight bellows "Get aff ma land!", pauses 0.5 s, then charges in a straight line at 2.5x speed until he hits a wall or the player. A wall stuns him for 1 s, so the player can dodge and make him run into walls. Melee crook swipe. | chase plus one "charge" state with a fixed velocity |
| **Exploding haggis** | **Kamikaze.** Scuttles fast and low at the player, fuse fizzing; explodes on contact or when shot (splash radius 96, hurts monsters too). Dormant ones wait under tables until the player is near. | chase plus the Mars bar's splash routine |
| **Tartan ghost** | **Floater that passes through walls.** Drifts straight at the player through one-sided walls (no collision: its sector is found by point-in-sector over the neighbours), drawn half-transparent (every other column), throws a cold "wail" projectile from range. Can only be hurt in a lit sector (light above 96), so the player lures it into torchlight. | no collision code; transparency is a column skip |
| **Midge swarm** | **Damage cloud.** A large, mostly transparent sprite of dots that drifts slowly at the player (ignores steps, blocked by walls) and does 1 damage every 5 tics while the player is inside its radius. Ordinary weapons do 1 damage (it has 200); one bagpipe blast disperses it. Spawns from bog sectors. | no attack state; damage is a radius check per tic |
| **Kelpie** | **Ambusher.** Waits submerged in a water sector (only its eyes drawn), lunges out with a bite when the player comes within 128, then retreats; never leaves water and adjacent sectors. | chase limited to a sector set |
| **Bogle** | **Ranged thrower.** Keeps 256-512 units away, strafes, lobs neeps in an arc. | reuses the thrown-arc projectile |
| **The Piper's Ghost** (boss) | Floats, plays a bagpipe blast of its own (the player's cone reversed: stun and knockback on the player), summons midges. | reuses the bagpipe and spawner code |

### 5.5 Pickups

Oatcake (+10 health); plate of haggis, neeps and tatties (+50); **Girder Juice** (a parody of

## 6. Testing

- **Pure core.** `game.braw` exposes `new_game(map)`, `tic(game, input)` (input = key bitmask +
  mouse dx) and `render(game, fb, w, h)`. Nothing in `engine/` calls the bridge, `mono_*`,
  `snooze` or random numbers (a seeded integer PRNG in game state instead). A test greps
  `engine/` for bridge names, float literals and float builtins.
- **Input recording.** `shell/main.braw` writes `replays/<name>.txt` when run with `--record`:
  one line per tic, `<keys bitmask> <mouse dx>`. Replays are text, small and diffable.
- **Headless runner.** `shell/headless.braw <map> <replay> <w> <h> <every>` runs every tic of
  the replay and renders and hashes every `every`-th frame, printing `tic hash` lines.
  Hash: FNV-1a 32-bit over the frame bytes, in mdhavers (integer `*`, `%`, `bit_xor`).
- **Parity.** `tests/bogle_parity.rs`: build `headless.braw` natively (`MDH_RC` off and on),
  run it and the interpreter at **80x50** for a 350-tic replay hashing every 35th frame; the
  three outputs must be identical, and must equal the committed `games/bogle/replays/*.hashes`
  (a deliberate rendering change re-blesses the file). Interpreter cost per 80x50 frame is in
  section 3.
- **Unit tests in mdhavers** (`games/bogle/tests/*.braw`, each prints `ok` lines, run by
  `tests/bogle_unit.rs` on the interpreter and native): fixed-point mul/div edges, trig table
  checksum, integer sqrt, map loader and validator (good map, and each validation failure),
  collision cases (slide, step up, too-low opening), inflate (stored, fixed, dynamic blocks;
  known vectors), PNG filters (one tiny PNG per filter type under `games/bogle/tests/png/`),
  baker output for a fixed input.
- **Bridge.** `tests/bogle_bridge.rs`: a native program calling every bridge name with
  `MDH_SCREEN=none` (the bridge's built-in offscreen mode: no window, `screen_shaw` hashes the
  converted BGRA frame to stderr), so bridge argument checks and palette conversion are tested
  without a display. Opening a real window is a manual check (stage 1 acceptance).
- Each new test is made to fail once before it is trusted (fleet rule).

## 8. Open questions for Arthur

1. **Interpreter graphics.** Add `screen_shaw`, `mouse_dx/dy`, `mouse_down` and
   `screen_grab_mouse` to the interpreter on the existing raylib window (2.4), so the game can be
   debugged in the interpreter? DEC round 7 left raylib "untouched for now". *Recommend yes*: it
   adds names and changes none, about 120 lines.
2. **Renderer.** Portal rendering over convex sectors instead of a Doom BSP (1.2). *Recommend
   portals*: no node builder, dynamic heights for free; the cost is that WAD loading (stage 7)
   needs a convex-cell conversion.
3. **Art pipeline.** Bake PNGs offline into raw `.bog` files committed beside the source art,
   rather than decoding PNGs at game start (4.2). *Recommend baking*: start-up and parity runs
   stay fast, and the decoder is still written in mdhavers and tested.
4. **Frame pacing.** No vsync in v1, a `snooze` to the next tic (2.3). *Recommend* accepting
   possible tearing in v1 and revisiting only if it shows.
5. **Native speed work.** Native already has 3x+ headroom at the pessimistic rate (section 3).
   Inline `bytes_get`/`bytes_set` anyway as a separate small lane? *Recommend later*, after
   stage 2, and only if a profile of the real renderer asks for it.
6. **Names.** `screen_shaw` (Scots "show") for presenting a frame, and "Girder Juice" as the
   Irn-Bru parody. *Recommend both*; either is a one-line rename.
7. **Pixel aspect.** Square pixels at 320x200 (16:10), not Doom's stretched 4:3. *Recommend
   square*: it suits current displays and makes integer scaling exact.
