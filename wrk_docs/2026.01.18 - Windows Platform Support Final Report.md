# Windows Platform Support - Final Review Report

**Date:** 2026-01-18
**Version:** 0.3.0
**Status:** Partially Complete - Threading Gap Identified

---

## Executive Summary

The Windows platform support implementation is **substantially complete** for most functionality, with one significant gap: the **LLVM runtime threading functions are stubbed on Windows**, despite the platform abstraction layer having full threading support.

| Component | Windows Status | Parity with Linux/WSL |
|-----------|----------------|----------------------|
| Interpreter (Rust) | Full | Identical |
| Audio Subsystem | Full | Identical |
| Graphics Subsystem | Full | Identical |
| LLVM Runtime - Core | Full | Identical |
| LLVM Runtime - Threading | **Stubs Only** | **Gap** |
| Platform Abstraction | Full | Identical API |

## Detailed Analysis

### 1. Platform Abstraction Layer

**Location:** `runtime/platform/`

The platform abstraction layer provides identical APIs across platforms:

| API Category | Functions | Unix Implementation | Windows Implementation |
|-------------|-----------|---------------------|----------------------|
| Directory Ops | `mdh_opendir`, `mdh_readdir`, `mdh_closedir` | POSIX `dirent.h` | `FindFirstFileW`/`FindNextFileW` with UTF-8 conversion |
| String Utils | `mdh_strcasecmp`, `mdh_strncasecmp` | `strcasecmp` | `_stricmp`/`_strnicmp` |
| Terminal I/O | `mdh_terminal_get_size`, `mdh_terminal_raw_mode`, `mdh_terminal_restore`, `mdh_terminal_read_char`, `mdh_terminal_input_available` | `termios`, `ioctl`, `poll` | Windows Console API (`GetConsoleScreenBufferInfo`, `SetConsoleMode`, `ReadConsoleInputW`) |
| Networking | `mdh_net_init`, `mdh_net_cleanup`, `mdh_socket_create`, `mdh_socket_close`, `mdh_socket_errno`, `mdh_poll` | POSIX sockets (no-op init) | Winsock2 (`WSAStartup`, `closesocket`, `WSAGetLastError`, `WSAPoll`) |
| Threading | `mdh_thread_create`, `mdh_thread_join`, `mdh_thread_detach`, `mdh_mutex_*`, `mdh_cond_*` | `pthread` | `CreateThread`, `SRWLOCK`, `CONDITION_VARIABLE` |
| Time | `mdh_time_monotonic_ns`, `mdh_time_realtime_ns`, `mdh_sleep_ms` | `clock_gettime`, `nanosleep` | `QueryPerformanceCounter`, `GetSystemTimeAsFileTime`, `Sleep` |
| Process | `mdh_shell_exec`, `mdh_shell_result_free`, `mdh_shell_status`, `mdh_mkstemp`, `mdh_unlink`, `mdh_getenv` | `popen`/`pclose`, `mkstemp`, `unlink` | `_popen`/`_pclose` via cmd.exe, `_mktemp_s`, `_unlink` |

**Verdict:** The platform layer provides **identical API semantics** on both platforms.

### 2. LLVM Runtime (`runtime/mdh_runtime.c`)

#### Fully Implemented on Windows

| Feature | Implementation |
|---------|---------------|
| Core runtime functions | All value operations, string manipulation, list/dict operations |
| Terminal input (`__mdh_get_key`) | Uses `mdh_terminal_read_char()` from platform layer |
| Terminal dimensions | Uses `mdh_terminal_get_size()` from platform layer |
| Directory listing | Uses `mdh_opendir`/`mdh_readdir`/`mdh_closedir` from platform layer |
| Shell execution | Uses `mdh_shell_exec()` from platform layer |
| Time functions | Uses `mdh_time_monotonic_ns()`, etc. from platform layer |
| Socket operations | Uses `mdh_socket_close()` from platform layer |
| Compatibility macros | `localtime_r`, `clock_gettime`, `close`, `dup`, `mkstemp` |

#### **GAP: Threading Functions (Stubs on Windows)**

The following LLVM runtime functions are **stubbed** and throw runtime errors on Windows:

```c
// Lines 3687-3736 in mdh_runtime.c
MdhValue __mdh_thread_spawn(...)   // "Threading isnae available on Windows yet"
MdhValue __mdh_mutex_new(...)      // "Threading isnae available on Windows yet"
MdhValue __mdh_condvar_new(...)    // "Threading isnae available on Windows yet"
MdhValue __mdh_atomic_new(...)     // "Threading isnae available on Windows yet"
MdhValue __mdh_chan_new(...)       // "Threading isnae available on Windows yet"
```

**Root Cause:** The Unix implementation (lines 3189-3686) uses `pthread` directly. The Windows stubs exist but don't use the platform layer's threading functions.

**Available in Platform Layer (unused):**
- `mdh_thread_create()` - `CreateThread`
- `mdh_thread_join()` - `WaitForSingleObject`
- `mdh_mutex_create()` - `InitializeSRWLock`
- `mdh_cond_create()` - `InitializeConditionVariable`

### 3. Interpreter (Rust)

The Rust interpreter has **full Windows parity**:

| Feature | Implementation |
|---------|---------------|
| Shell commands | `#[cfg(target_os = "windows")]` uses `cmd /C`, else `sh -c` |
| File operations | Cross-platform `std::fs` |
| Path handling | Cross-platform `std::path` |
| Audio | Unified audio abstraction (miniaudio or raylib backend) |
| Graphics | raylib (cross-platform) |
| Networking | Rust's cross-platform `std::net` + `trust-dns-resolver` |

**Test Results:** 129 test suites pass on Windows (without LLVM/graphics features).

### 5. Build System

**Status: Full Parity**

`build.rs` correctly handles both platforms:

```rust
if target.contains("windows") {
    build.file("runtime/platform/platform_win32.c");
    println!("cargo:rustc-link-lib=ws2_32");
    println!("cargo:rustc-link-lib=userenv");
} else {
    build.file("runtime/platform/platform_unix.c");
    println!("cargo:rustc-link-lib=pthread");
}
```

Static library naming handled:
- Windows: `mdh_runtime_rs.lib`
- Unix: `libmdh_runtime_rs.a`

## Recommendations

### Immediate (No Code Changes Required)

1. **Document the threading limitation** - Update README to note that LLVM-compiled programs using threading builtins are not supported on Windows yet.

### Short-Term (To Achieve Full Parity)

1. **Implement Windows threading in mdh_runtime.c** - Refactor the `#ifndef _WIN32` threading block (lines 3189-3686) to use the platform layer:
   - Replace `pthread_t` with `mdh_thread_t*`
   - Replace `pthread_mutex_t` with `mdh_mutex_t*`
   - Replace `pthread_cond_t` with `mdh_cond_t*`

   Estimated effort: 2-3 hours

2. **Add platform-layer atomic operations** - The platform layer doesn't currently wrap atomic operations. Windows uses `InterlockedExchange*` functions vs. GCC's `__atomic_*` builtins.

### Long-Term

1. **DTLS support on Windows** - Currently Unix-only due to OpenSSL vendored build. Would require Windows OpenSSL or alternative.

## Conclusion

Windows platform support is **substantially complete** with identical functionality to Linux/WSL for:
- All interpreter features
- Audio and graphics
- File I/O, networking, terminal I/O
- Shell command execution
- LLVM compilation (core features)

The only gap is **LLVM runtime threading**, which is stubbed despite the platform abstraction layer being ready. This affects programs that use:
- `thread_spawn()`, `thread_join()`
- `mutex_new()`, `mutex_lock()`, `mutex_unlock()`
- `condvar_new()`, `condvar_wait()`, `condvar_signal()`
- `chan_new()`, `chan_send()`, `chan_recv()`
- `atomic_new()`, `atomic_load()`, `atomic_store()`

For non-threaded LLVM programs and all interpreter usage, **Windows and Linux/WSL have identical functionality**.
